# 开发过程与工作流程说明 · AI Panel Studio

> 对应原需求「开发过程思路 & 工作流程说明（1–1.5 页）」。
> 一句话：**先定契约，再让 AI 写；AI 写的每一段都要能被测试或文档验证，验证不过就改契约或改代码，不靠"看起来对"。**

## 1. 开发流程（六段，每段有明确输入/输出/验收）

| 阶段 | 输入 | 我让 AI 做什么 | 输出 | 验收方式 |
| --- | --- | --- | --- | --- |
| M0 文档 | 原需求（截图留档 `docs/assets/`） | 拆需求、出 PRD/架构/ER/API/测试/计划初稿 | 9 份 md + mermaid 图 | 逐条对照原需求打勾；每条 FR 必须有验收标准 |

| M2 组局 | API 契约 + 席位字段 | 生成议题分析 prompt、席位流式接口、用户选座/自动开场、开场前认领、大厅/组局页 | 能发起 5 席圆桌：自选一席，其余 AI 补齐并自动开场 | 集成 I-1~I-4；刷新后状态保持 |

关键纪律：**每段结束先跑验收，再进下一段**。AI 一次给太多代码时，宁可拆成"契约 → 实现 → 测试"三轮，也不一次性接收。

## 2. 工具与模型怎么用

- **工具**：本次在 **CodeBuddy（Vibe Coding 工具，Agent 模式）** 内完成，具备文件读写、命令执行、截图裁剪等能力；不使用浏览器版 AI 对话产物。
- **模型**：底层为 DeepSeek 系列推理模型。原需求示例给的组合是"Claude Code + DeepSeek V4 Pro"，本质是**编码代理 + 强推理模型**，本项目流程可直接迁移（换工具只换执行器，不换方法）。
- **任务边界与权限**（我会在每次开新会话时先声明）：

  | 项 | 约定 |
  | --- | --- |
  | 可写范围 | 仅 `D:\rep\ai-panel-studio` 仓库内 |
  | 禁止动作 | 改 `.git` 历史、删 `data/`、装全局依赖、访问仓库外用户文件 |
  | 依赖引入 | 需我确认，避免引入与项目约定冲突的包 |
  | 提交 | AI 只改文件，`git commit` 由我审核后执行，message 我定 |

- **为什么用 Agent 模式**：本任务跨"文档 → 多模块代码 → 测试 → 打包"多步，且需要按文件粒度反复修改；单轮问答无法保持上下文一致，Agent 能在同一工作区内连续读写并自查（如提交前跑 `grep` 清理残留）。
- **上下文管理**：长任务按阶段切会话；每次只带当前阶段必需文件（如做 SSE 时只给 ARCHITECTURE §3.3 + API §3 + 相关源码），避免上下文过长导致"忘掉前面的约束"。

## 3. 三个典型问题与解决路径

### P1 · 多 Agent 并行被写成串行

- **现象**：AI 初稿用 `future.get()` 逐个等待，代码"看起来并行"，实际 A 慢就会挡住 B；SSE 也写成每 agent 一条连接。
- **定位**：E2E-2 里让 A 延迟 8s、B 延迟 1s，断言 B 的 `message.end` 早于 A —— 直接暴露串行。
- **修正**：`CompletableFuture.allOf(...).handle(...)` 扇出；单条消息独立 `messageId`，**一条 SSE 连接按 id 多路复用**；发送侧按 60–80ms 合并 delta（避免 `SseEmitter` 写锁排队）。
- **结果**：并行证据可量化（时间戳先后），不靠"感觉"。

### P2 · 原需求存在版本差异，口径对不上

- **现象**：同一天拿到两份措辞不同的说明（数量要求、交付物清单都不一致），文档一度按旧版写，导致交付项对不上。
- **定位**：把两份截图裁出关键段落（`docs/assets/`）逐条比对，列出差异表，而不是凭印象判断。
- **修正**：①以最新版为准，旧版中不冲突的量化要求保留为加分项；②所有结论标注依据出处（DELIVERY §5 版本差异核对表）；③交付清单按现行版重排。
- **结果**：避免了"交付件格式不对"和"漏交 Prompt 记录"这类一票否决的错误。

### P3 · SQLite 单写者与流式落库冲突

- **现象**：AI 初稿把"消息落库"放在一个包住 LLM 调用的大事务里，长讨论下写锁被占死，其他讨论的写全部 `SQLITE_BUSY`。
- **定位**：并发写用例（I-13）压 20 条 `message.end`，观察 `busy` 计数与 P95。
- **修正**：①**禁止在事务内调 LLM / 发 SSE**；②delta 不落库，只在 `message.end` 一次 `UPDATE`；③`busy_timeout=5000` + 50/100/200ms 退避重试；④连接池只开 4。
- **结果**：写量降到 1/300，长讨论不再阻塞其他圆桌。

> 另有一类"AI 走偏"是**旧内容残留**（换栈后仍出现 `docker compose`、`Prisma`）：解决方式是提交前 `grep` 全量扫描关键词，并写进交付自检清单。

## 4. 我对"工程化 AI 开发"的理解

1. **契约先行**：先有 PRD/ER/API，AI 才有"靶子"。没有契约时 AI 会自己发明字段，后面全是返工。本项目换过三次技术栈（Node→Spring、PostgreSQL→SQLite、容器→本地脚本），**业务接口一行没改**，就是契约的价值。
2. **测试是 AI 的缰绳**：AI 很擅长写出"看起来对"的并发代码。把人能看懂的断言（时间戳先后、幂等、刷新后仍在）先写出来，AI 才没有发挥空间去糊弄。
3. **可追溯比"写得快"重要**：每个决策留一条记录（为什么不用 WebFlux、为什么不用 `SELECT FOR UPDATE`），评审问起来能答，自己回头看也不会推翻。
4. **人守住三件事**：需求边界、并发/事务正确性、产品观感。其余（样板代码、文档排版、用例骨架）交给 AI 是划算的。
5. **AI 的产出必须可验收**：不能验收的产出，本质上等于没做。
