# ADR-001 · 前端 UI 方案：是否采用 Element Plus / Element

| 项 | 内容 |
| --- | --- |
| 状态 | **已决策：不采用任何 UI 组件库，UI 全部手写** |
| 日期 | 2026-11-17 |
| 决策者 | 项目负责人（人工拍板） |
| 关联 | [PRD](PRD.md) §4.4/§8 · [ARCHITECTURE](ARCHITECTURE.md) §4 · [README](../README.md) §3 |
| 结论一句话 | **技术上可行，项目上不可行** —— Element Plus 能承担 UI 层，但违反作业硬性约束，且解决不了本项目最核心的三色席位 / 消息流 / 轨迹三个界面 |

---

## 1. 背景与约束

| 项 | 内容 |
| --- | --- |
| 前端栈 | Vue 3.4 + TypeScript + Vite 5 + Pinia 2 + Vue Router 4 |
| 界面要求 | **全中文 UI**；三个角色视觉可区分；三档响应式；"像在旁观一场圆桌" |
| 硬性约束 | 作业「注意事项」第 2 条：**严禁使用任何 UI 框架/组件库（如 Ant Design、Element Plus），必须手写全部 UI** |
| 待回答 | Element Plus / Element 能不能当前端框架？如果能，要不要用？ |

> 先厘清概念：Vue 3 本身是**框架**（已采用）；Element Plus 是**组件库**（提供 Button/Dialog/Table 等现成 UI）。问题实质是"要不要引入组件库"，不是"换不换框架"。

## 2. 候选方案

| 编号 | 方案 | 说明 |
| --- | --- | --- |
| A | **Element Plus 2.x** | Element 的 Vue 3 版本，国内使用最广 |
| B | **Element UI 2.x** | Vue 2 时代版本，已停止新功能开发 |
| C | 其他中文生态组件库 | Naive UI / Ant Design Vue / Arco Design Vue |
| D | **纯手写（Vue SFC + 原生 CSS + CSS 变量）** | 当前方案 |

## 4. 四个关键判断

### 4.1 合规是硬门槛，不是风格偏好

作业原文直接点名 "Element Plus"，还补了一句"必须手写全部 UI"。用了它，等于主动提供"未遵守约束"的证据 —— 前端体验 15 分是小账，整体印象与"是否认真读题"是大账。这一条足以单独否决 A/B/C。

### 4.2 组件库解决不了本项目最难的 70%

圆桌页面真正难的是：席位状态点（呼吸动画）、消息气泡的流式打字与引用徽标、轨迹时间线的折叠、"先到先占位"的并行渲染。这些 Element Plus 一个组件都没有。引入组件库只省下按钮、弹窗、输入框约 30% 的工作量，却要额外适配一套设计语言 —— 投入产出倒挂。

### 4.3 "中文 UI" 不等于"中文组件库"

Element Plus 的默认文案是英文，要中文必须挂 `ConfigProvider locale=zhCn`；即便挂上，日期格式、上传状态、无障碍属性仍有英文残留。而本项目的界面文案量不大但要求口径统一（议题/席位/回合/纪要），手写一个 `lib/copy.ts` 常量表反而更彻底、更可控。

### 4.4 Element（Vue 2 版）根本不适用

`Element UI` 只支持 Vue 2；Vue 3 项目要用得靠 `@vue/compat` 兼容层，官方已明确不推荐用于新项目。所以即便要引入组件库，候选也只能是 Element Plus，而它已因 4.1 被否。

## 5. 决策

| 项 | 决定 |
| --- | --- |
| UI 实现 | **Vue SFC + 原生 CSS + CSS 变量，全部手写** |
| 是否引入 Element Plus / Element / 其他组件库 | **否** |
| 依赖白名单 | `vue` `vue-router` `pinia` `vite` `typescript` + 测试工具；**不含任何 UI 组件库** |
| 约束落地 | code review 检查 `package.json`，出现 UI 组件库依赖即打回 |

## 6. 中文 UI 规范（本项目如何做到"中文"）

| 项 | 规范 |
| --- | --- |
| 语言 | 界面文案 100% 简体中文，不出现 OK / Cancel / Submit / Loading / No Data |
| 术语表 | 圆桌、议题、席位、认领、回合、发言、插话、轨迹、纪要、溯源、收敛（统一口径，前后端错误文案共用） |
| 相对时间 | 刚刚 / 3 分钟前 / 2 小时前 / 昨天 16:32 / 2026-11-17 |
| 绝对时间 | `2026-11-17 16:32`，24 小时制，不用 AM/PM |
| 数字与单位 | 中文与数字间加空格："3 个席位"、"第 2 回合"；百分比 "38%" |
| 标点 | 中文全角标点；中英混排时空格分隔（"SSE 连接中断"） |
| 文案语气 | 短句、动词开头；错误文案必须给"原因 + 下一步"，例如："模型服务超时，已保留已生成内容，可重试" |
| 空态 | 一句解释 + 一个动作："还没有圆桌，发起第一场？" |
| 字号/行高 | 正文 15/1.7，标题 20/28，讨论流最大行宽 720px（中文长文可读性） |
| 字体栈 | `-apple-system, "PingFang SC", "Microsoft YaHei", "Source Han Sans SC", sans-serif`（Windows 优先雅黑） |
| 无障碍 | `aria-label` 用中文（"认领技术专家席位"）；流式输出 `aria-live="polite"` + 500ms 节流 |
| 三色令牌 | `--seat-amber: #B45309`（战略顾问）· `--seat-teal: #0F766E`（行业分析师）· `--seat-indigo: #3730A3`（技术专家）· `--seat-slate`（主持）· `--seat-emerald`（你）；相邻色明度差 ≥ 12%，照顾色觉差异 |

## 7. 如果将来必须引入组件库（预留，不实现）

| 项 | 内容 |
| --- | --- |
| 触发条件 | 需求扩展到富表单（树选择、可编辑表格、复杂分页），或工期紧到无法手写 |
| 架构预留 | 业务组件**不得直接 import 第三方 UI**；只允许通过 `components/base/`（BaseButton / BaseDialog / BaseInput / BaseSelect）间接使用 |
| 迁移成本 | 只改 `base/` 内 4–6 个文件，业务页面零改动 |
| 代价 | 包体增加、视觉需重新覆盖一轮、与"手写 UI"的要求再次冲突（届时需与评审方确认） |

> 本 ADR 只约束"依赖方向"，不预置代码 —— 不为一个不打算发生的迁移写抽象层。

---

## 8. 后果

- **正面**：零组件库依赖，包体最小；视觉完全为圆桌场景服务；合规；CSS 变量体系让三色调色一处生效。
- **负面**：多写约 600 行 CSS；表单细节（焦点管理、Esc 关闭、焦点陷阱）需自己实现。
- **缓解**：键盘走查清单 + E2E 断言（Tab 可达、Esc 可关、焦点不丢），把"手写容易漏"的部分固化成测试。
