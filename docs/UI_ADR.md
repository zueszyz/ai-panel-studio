# ADR-001 · 前端 UI 方案：Element Plus / Element 可行性分析

| 项 | 内容 |
| --- | --- |
| 状态 | **已决策：不采用 Element Plus / Element，UI 由项目手写**（依据版本见 §10） |
| 日期 | 2026-11-17 |
| 决策者 | 项目负责人（人工拍板） |
| 关联 | [PRD](PRD.md) §4.4/§8 · [ARCHITECTURE](ARCHITECTURE.md) §4 · [README](../README.md) §3 |
| 一句话结论 | **Element Plus 技术上可以作为本项目的前端 UI 层，且在现行作业说明下不受限；Element 因只支持 Vue 2 直接出局。综合评估后仍不采用 —— 不是因为违规，而是因为收益不抵成本。** |

## 1. 依据：现行作业说明怎么写的

| 原文（要点） | 对本决策的含义 |
| --- | --- |
| 「数据库采用 SQLite」 | 数据库已限定，与本 ADR 无关（但影响前端数据形态：无分页大表，列表都是小集合） |
| 「**前端及后端框架不限，选择你最擅长的即可**」 | **没有禁止 UI 组件库**；Vue 3、Element Plus、Ant Design Vue 都在允许范围内 |
| 「原创性：必须从 0 到 1 创建」 | 不禁止使用现成库，但强调"自己做出来"的过程与结果 |
| 「以演播厅视觉风格与交互设计要素深度驱动前端组件与状态流转」 | 视觉与交互是评分点，需要**为这个场景定制**，而不是套通用后台模板 |
| 「UI 是否真的像在观看一场演播厅讨论」 | 核心考察点之一：观感必须贴合"圆桌/演播厅"，不能像管理后台 |

> **重要更正**：本项目早期文档曾把"严禁使用任何 UI 框架/组件库（如 Ant Design、Element Plus）"写成硬性约束 —— 那是**另一版作业说明**的措辞，与本版不一致（详见 §10）。按现行说明，组件库是**允许**的；本 ADR 的"不采用"属于**项目自选**，而非合规强制。

### 1.1 允许 ≠ 必须：这条边界要分清

| 说法 | 是否成立 |
| --- | --- |
| "作业禁止使用 Element Plus" | ❌ 不成立（本版明确"框架不限"） |
| "作业不禁止应用框架，因此 Vue 3 合规" | ✅ 成立 |
| "既然允许，就应该用组件库以省时间" | ❌ 不成立 —— 允许只是去掉合规门槛，是否划算要单独算（见 §3、§4） |
| "本项目不使用组件库" | ✅ 成立 —— 这是**技术选型结论**，理由在下面，不是"被迫" |

## 2. 候选方案

| 编号 | 方案 | 定位 |
| --- | --- | --- |
| A | **Element Plus 2.x** | Element 的 Vue 3 版本，国内使用最广的 Vue 3 组件库 |
| B | **Element UI 2.x** | Vue 2 时代版本，已停止新功能开发 |
| C | 其他中文生态组件库 | Naive UI / Ant Design Vue / Arco Design Vue |
| D | **纯手写（当前方案）** | Vue SFC + 原生 CSS + CSS 变量 |

## 3. 可行性评估矩阵

| 维度 | A. Element Plus | B. Element | C. 其他组件库 | D. 纯手写 |
| --- | --- | --- | --- | --- |
| **能否作为前端框架的 UI 层** | ✅ 可以（Vue 3 插件式注册，配合 Vite 按需引入） | ❌ 不可以（仅 Vue 2；Vue 3 需 `@vue/compat`，官方不推荐新项目使用） | ✅ 可以 | ✅ 本身就是实现方式 |
| 是否符合现行作业说明 | ✅ 允许（框架不限） | ❌ 技术不兼容 | ✅ 允许 | ✅ 允许 |
| 中文文档/生态 | ✅ 完善 | 🟡 已过时 | 🟡 视库而定 | — |
| 中文化成本 | 🟡 需 `ConfigProvider locale=zhCn`；日期、上传、无障碍属性仍有英文兜底 | 🟡 同上 | 🟡 同上 | ✅ 自建 `copy.ts`，100% 可控 |
| 主题可控性 | 🟡 CSS 变量可覆盖，但默认圆角/阴影/蓝色主色辨识度强 | 🟡 同 A | 🟡 同 A | ✅ 完全可控 |
| **与本项目核心界面的匹配度** | ❌ 三色席位、消息气泡流式、轨迹时间线、席位状态点**均无现成组件** | ❌ | ❌ | ✅ 为场景而写 |
| 可复用的部分 | 🟡 按钮、弹窗、输入框、滚动条、消息提示（约占界面工作量 30%） | 🟡 | 🟡 | — |
| 包体（gzip） | 🟡 按需引入约 +100KB | 🟡 | 🟡 | ✅ 0 |
| 首屏 / 流式渲染压力 | 🟡 额外 CSS/JS 占用主线程 | 🟡 | 🟡 | ✅ 最轻 |
| 视觉辨识度（"像演播厅"） | 🟡 默认观感偏"后台管理系统"，需大量覆盖才能贴合 | 🟡 | 🟡 | ✅ 从零设计 |
| 长期维护 | 🟢 活跃 | 🔴 停滞 | 🟡 | 🟢 代码在自己手里 |

**结论**：A 可行且合规；B 技术不可行；C 同 A；D 可行且最贴合场景。

## 4. 四条决定性判断

### 4.1 Element（Vue 2 版）在技术上直接出局

`Element UI` 只支持 Vue 2。本项目前端是 Vue 3.4，要用只能挂 `@vue/compat` 兼容层，官方明确不建议用于新项目 —— 等于给自己埋一个"组件行为与文档不一致"的长期坑。**所以"Element 或 Element Plus"这个二选一，实际只有 Element Plus 一个候选。**

### 4.2 Element Plus 只能覆盖约 30% 的界面

本项目界面真正的工作量在：

| 界面 | 是否有现成组件 |
| --- | --- |
| 席位卡（头像 + 岗位 + 立场 + 呼吸状态点 + 认领态） | ❌ 无 |
| 消息气泡（左侧色条 + 轮次徽标 + 流式打字 + 引用徽标 + 失败重试态） | ❌ 无 |
| 轨迹时间线（思考/生成/完成三态 + 折叠技术细节 + 与消息联动定位） | ❌ 无 |
| 三色设计令牌体系 | ❌ 无（组件库只给一套默认主色） |
| 按钮 / 弹窗 / 输入框 / 滚动条 | ✅ 有 |

引入组件库省下的是最后一行，代价是给前四行再套一层必须覆盖的主题 —— **投入产出倒挂**。

### 4.3 中文 UI 不等于中文组件库

Element Plus 默认文案是英文，要中文得挂 `ConfigProvider locale=zhCn`；即便挂上，日期格式化、上传状态、部分无障碍属性仍是英文。本项目界面文案量不大但要求口径统一（议题/席位/回合/纪要/溯源），自建一个 `lib/copy.ts` 常量表反而更彻底、更容易做到"零英文残留"，也更符合"全中文 UI"这条要求。

### 4.4 视觉辨识度是评分点，"默认观感"会稀释它

现行说明把「UI 是否真的像在观看一场演播厅讨论」列为考察点。Element Plus 的默认观感（圆角、阴影、蓝色主色、后台式表格）辨识度极强，一眼就是"套了个管理后台"；要抹掉这层观感，需要重写大量样式 —— 与其如此，不如一开始就按演播厅/圆桌场景设计。

## 5. 决策

| 项 | 决定 |
| --- | --- |
| 是否采用 Element Plus | **否**（可行、合规，但不划算） |
| 是否采用 Element | **否**（与 Vue 3 不兼容，技术上不可行） |
| 是否采用其他 UI 组件库 | **否**（同 A 的成本结构） |
| UI 实现 | Vue SFC + 原生 CSS + CSS 变量（`tokens.css` 定义三色/间距/字号） |
| 依赖白名单 | `vue` `vue-router` `pinia` `vite` `typescript` + 测试工具；不含任何 UI 组件库 |
| 复核方式 | code review 检查 `package.json`，出现 UI 组件库依赖需说明理由 |

### 5.1 什么情况下会改变这个决定

| 触发条件 | 届时怎么做 |
| --- | --- |
| 需求扩展到富表单（树选择、可编辑表格、级联） | 引入 Element Plus，但只允许通过 `components/base/` 使用（见 §7） |
| 工期被压缩到无法手写 | 同上；优先复用 Dialog / Message / Scrollbar 三类基础件 |
| 评审明确要求"用组件库" | 同上；同时保留手写主题覆盖，保证三色与演播厅观感 |

## 6. 中文 UI 规范（本项目如何做到"中文"）

| 项 | 规范 |
| --- | --- |
| 语言 | 界面文案 100% 简体中文，不出现 OK / Cancel / Submit / Loading / No Data |
| 术语表 | 圆桌、议题、席位、认领、回合、发言、插话、轨迹、纪要、溯源、收敛（前后端错误文案共用同一口径） |
| 相对时间 | 刚刚 / 3 分钟前 / 2 小时前 / 昨天 16:32 / 2026-11-17 |
| 绝对时间 | `2026-11-17 16:32`，24 小时制，不用 AM/PM |
| 数字与单位 | 中文与数字间加空格："3 个席位"、"第 2 回合"、"38%" |
| 标点 | 中文全角标点；中英混排空格分隔（"SSE 连接中断"） |
| 文案语气 | 短句、动词开头；错误文案必须给"原因 + 下一步"：「模型服务超时，已保留已生成内容，可重试」 |
| 空态 | 一句解释 + 一个动作：「还没有圆桌，发起第一场？」 |
| 字号/行高 | 正文 15/1.7，标题 20/28，讨论流最大行宽 720px |
| 字体栈 | `-apple-system, "PingFang SC", "Microsoft YaHei", "Source Han Sans SC", sans-serif` |
| 无障碍 | `aria-label` 用中文（"认领技术专家席位"）；流式输出 `aria-live="polite"` + 500ms 节流 |
| 三色令牌 | `--seat-amber: #B45309`（战略顾问）· `--seat-teal: #0F766E`（行业分析师）· `--seat-indigo: #3730A3`（技术专家）· `--seat-slate`（主持）· `--seat-emerald`（你）；相邻色明度差 ≥ 12% |

## 7. 预留：若将来引入组件库的迁移路径（当前不实现）

| 项 | 内容 |
| --- | --- |
| 依赖方向 | 业务组件**不得直接 import 第三方 UI**，只允许通过 `components/base/`（BaseButton / BaseDialog / BaseInput / BaseSelect / BaseScroll）间接使用 |
| 迁移成本 | 只改 `base/` 内 4–6 个文件，业务页面与 store 零改动 |
| 代价 | 包体增加、主题需重新覆盖一轮、观感调和 |
| 当前状态 | 只写约定，不预置抽象层 —— 不为一个不打算发生的迁移增加复杂度 |

## 8. 后果

- **正面**：零组件库依赖，首屏最轻；三色席位与演播厅观感完全自主；中文文案 100% 可控；不存在"版本升级导致组件行为漂移"的风险。
- **负面**：多写约 600 行 CSS；表单细节（焦点管理、Esc 关闭、焦点陷阱）需自己实现。
- **缓解**：把"手写容易漏"的部分固化成测试 —— 键盘走查（Tab 可达、Esc 可关、焦点不丢）+ E2E 断言。
